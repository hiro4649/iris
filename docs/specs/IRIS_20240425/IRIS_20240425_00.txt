## Phase00 完全拘束版（最終整合版・単体完結版）

## 00. 文書の役割

本仕様書は IRIS 開発全体の最上位拘束文書である。
Phase01 以降の仕様、設計、実装、テスト、ログ、運用判断は、本仕様書に従わなければならない。

本書の役割は、IRIS を賢くすることではない。
IRIS が後続フェーズで壊れないようにすることだ。

ここで固定するのは以下である。

Core / Adapter 境界
Event / Action / Task / Review Queue 契約
Phase 間 I/O 契約
命名規則
ID 規則
Memory segmentation
Source of Truth
Global fail / stop
Producer / Consumer の責務
Task → Action → World Command の経路制約
review path の正式接続先
side input の許可条件
CI による境界検証条件

本書に未定義の挙動は実装禁止とする。
「後で決める」「実装者判断で補完する」は禁止する。
未定義は未実装である。

## 01. 最終目的

Phase00 の最終目的は以下の状態を固定することにある。

IRIS Core が platform-agnostic であること。
IRIS が複数世界に複数 Presence を持っても、人格主体は 1 つであること。
Core と Adapter の責務境界が壊れないこと。
全フェーズの入出力が機械的に接続できること。
全フェーズの命名、score、ID、fail 条件が衝突しないこと。
world-specific 情報が core continuity を汚染しないこと。
task_type から world_command へ直接飛ばないこと。
外部観測が source of truth にならないこと。
Phase01〜07 が本書を上位拘束として共有すること。
review path と通常 path が衝突しないこと。
side input が暗黙入力ではなく契約入力として固定されること。
action_type の決定責務が 1 箇所に固定されること。

## 04. IRIS の最上位原則

IRIS はゲーム NPC ではない。
IRIS は YouTube、Minecraft、VRChat など複数世界を横断して継続する単一 AI character である。
複数 Presence は許可するが、複数人格は許可しない。
Core は schema と phase contract を理解し、world-specific 実行は Adapter が担当する。
Adapter は変換だけを行い、判断してはならない。
外部観測は reference であり truth ではない。
Phase00 はこの原則に反するすべての実装を fail とみなす。

---

## 05. 全体アーキテクチャ

唯一許可される通信構造は以下である。

```text
Adapter -> EventBus -> Core -> EventBus -> Adapter
```

これ以外の通信は禁止する。
Core から Adapter を直接呼んではならない。
Core が world_command を生成してはならない。
Adapter が intent や memory を生成してはならない。
EventBus は publish / subscribe 以外のロジックを持ってはならない。

review path を使う場合も、Core 内の許可済み consumer を経由しなければならない。
review path を理由に Core / Adapter 境界を破ってはならない。

---

## 06. Core 定義

Core は以下のみを持つ。

Event を受ける。
Schema を検証する。
Phase ごとの canonical export を返す。
Phase ごとの内部処理を行う。
review path を受ける正式 consumer を持つ。
source of truth と route 制約を守る。

Core が持ってはならないものは以下である。

world SDK import
world 名分岐ロジック
Adapter 直接呼び出し
world_command 生成
memory 永続更新
goal 生成
trait 生成
外部観測の truth 化
暗黙 side input
契約外 field 補完

Core は schema-driven でなければならない。

---

## 07. Adapter 定義

Adapter の責務は以下のみである。

raw event の normalize
canonical Event への変換
Action 契約の serialize
world_command への変換
transport / timeout / world-specific parameter の処理

Adapter が持ってはならないものは以下である。

intent 生成
memory 更新
relation 解釈
goal 生成
character 判定
safe redirect 判定
task 評価
人格変更
state 永続保持
action_type の変更
review queue の解釈

Adapter は変換器であり、意思決定器ではない。

---

## 08. EventBus 定義

EventBus は唯一の通信経路である。
役割は publish / subscribe のみとする。

以下は禁止する。

ロジック
状態保持
retry policy
priority 再解釈
schema 以外の暗黙変換
phase 跨ぎの field 補完
truth 判定

## 09. Event Schema

Event の canonical 形式は以下に固定する。

```json
{
  "event_id": "uuid",
  "trace_id": "uuid",
  "source": "youtube|minecraft|vrchat|system",
  "timestamp_ms": 0,
  "payload": {}
}
```

必須条件は以下とする。

`event_id` 欠落は reject
`trace_id` 欠落は reject
`source` 不正値は reject
`timestamp_ms` 型不一致は reject
`payload` 非 object は reject

Phase01 で以下の補助値を Adapter が normalize して追加してよい。

```json
{
  "target_presence_id": "uuid|null",
  "mention_flag": false,
  "priority": 0
}
```

ただし Adapter は intent を決めてはならない。

必須条件は以下とする。

`target_presence_id` 欠落は reject
`parameters` 非 object は reject

Action は world_command ではない。
Action は Core 側の共通行動粒度である。
Adapter は Action を world_command に変換してよいが、`action_type` を変更してはならない。

## 11. Presence Schema

Presence の最小 canonical 形式は以下に固定する。

```json
{
  "presence_root_id": "uuid",
  "presence_id": "uuid",
  "world": "youtube|minecraft|vrchat",
  "status": "active|idle|blocked"
}
```

制約は以下とする。

`presence_root_id` は全 instance 共通
`presence_id` は一意
`blocked` Presence は action 出力先になれない
同時に speaker_token を持てる Presence は 1 つまで

## 12. Identity 最小定義

identity は world 跨ぎの人物候補または確定対象である。
同名で自動 link してはならない。
confidence threshold なしの auto-confirm を禁止する。

最小 state は以下とする。

```text
UNLINKED
CANDIDATE
LINKED
UNSAFE
BLOCKED
```

初期フェーズでは `UNLINKED|CANDIDATE` のみ使用してよい。
ただし threshold なし auto-link 禁止は全フェーズ共通 hard rule とする。

## 13. ID ルール

全フェーズで必須の ID は以下である。

`trace_id`
単一の end-to-end 処理単位を追跡する ID

`event_id`
単一入力イベントを識別する ID

`presence_root_id`
単一人格に紐づく Presence 群を束ねる ID

`presence_id`
各 world instance の一意 ID

`task_id`
Phase07 の task 単位 ID

`queue_id`
review queue 単位 ID

ルールは以下とする。

trace_id は phase を跨いで変えてはならない。
event_id は review path でも原イベント単位を保持する。
phase-local ID を global ID の代わりに使ってはならない。
ログ、export、error の全相関は trace_id を基準とする。

## 14. Memory segmentation

Memory segmentation は以下に固定する。

```text
core_identity
relational
episodic
semantic
working
world_specific
safety_memory
```

各領域の意味は以下とする。

`core_identity`
IRIS の人格核。Phase05 以前で更新禁止。Phase06 でも直接上書き禁止。

`relational`
対象との関係性の低速更新領域。

`episodic`
イベント単位の履歴。

`semantic`
圧縮された意味情報。

`working`
runtime 一時記憶。永続対象ではない。

`world_specific`
世界固有の一時情報。core continuity を上書きしてはならない。

`safety_memory`
安全系拘束。Phase05 で直接更新禁止。

## 21. Source of Truth の上位原則

優先順位は以下に固定する。

```text
Character
> Runtime State
> Persistent Memory
> External Observation
```

全フェーズ共通 hard rule は以下とする。

External Observation を truth として採用してはならない。
Character 制約に反する更新を commit してはならない。
Persistent Memory が Character を上書きしてはならない。
Runtime State が Character 制約と衝突する場合、commit してはならない。
Character は上書き対象ではなく検証制約である。

---

## 22. 経路制約

全フェーズ共通 hard rule として、必ず以下を守ること。

```text
task_type -> action_type -> world_command
```

以下は禁止する。

task_type -> world_command
intent -> world_command
reaction -> world_command
task_type -> skill を飛ばした直接 SDK call
Phase07 からの直接 world 実行
Adapter による action_type の変更

補足拘束を以下に固定する。

action_type の canonical 決定権は Phase04 にのみ存在する。
Phase02 は reaction-level 信号を producer するが、action_type を確定してはならない。
Phase07 は task_type を生成できるが、task_type から world_command へ直接到達してはならない。
review path は memory / persistence 系の再評価を目的とし、実行系 shortcut に使ってはならない。

---

## 23. Phase 間 I/O 契約の原則

Phase 間接続は自由結線してはならない。
各フェーズの producer / consumer は、本章の I/O 契約表に従って固定する。

Phase00 は基礎 schema と global rule を producer する。
Phase01 は intent / presence / working context を producer する。
Phase02 は reaction / variation / micro expression を producer する。
Phase03 は compact context signal を producer する。
Phase04 は world 非依存 action 契約を producer する。
Phase05 は persistence 評価済み update を producer する。
Phase06 は sync 済み状態を producer する。
Phase07 は task 実行評価と memory update review queue を producer する。

各 phase は、Phase00 の I/O 契約表で許可された producer の canonical 出力のみを consumer してよい。
直前 phase のみを consumer しなければならない、という意味ではない。
許可されていない phase の出力を暗黙参照してはならない。
raw payload 全文を勝手に再参照してはならない。
不足フィールドを暗黙補完してはならない。
side input を使う場合は、本章に `Required` `Optional` `Side Input` を明示しなければならない。

## 25. review path 定義

review path は通常 path と分離された正式経路である。
用途は以下に限定する。

Phase07 実行評価の結果を Phase05 の review intake に戻すこと
memory / persistence 候補の再評価を要求すること
character_feedback を persistence 評価へ補助入力として渡すこと

review path で以下を行ってはならない。

world_command 実行
Phase04 への action shortcut
Phase06 への同期 shortcut
direct memory write
通常 path の required key を省略した再投入

Phase05 は通常入力 source として Phase04 export を受ける。
さらに review path consumer として Phase07 queue を受ける。
この 2 経路を同一入口で曖昧 merge してはならない。
review intake は明示的に別 consumer として持たなければならない。

全フェーズ共通で phase prefix を必須とする。

```text
phase07_value_score

phase07_character_alignment_score

phase07_reputation_score
```

`character_fit` `value_reward` `character_reward` は canonical score 名として使用してはならない。
必要であれば phase 内部一時変数または queue 生成前の補助計算値としてのみ保持し、export field 名には使ってはならない。

```text
REVIEW_PATH_VIOLATION
```

phase-local stop reason は `PHASE{NN}_*` 接頭辞を必須とする。

優先順位は以下とする。

trace / schema 系

> source of truth / character 系
> rollback / sync 系
> export / review path 系

複数同時発火時は上位を primary reason として記録し、下位を secondary reason として evidence に残すこと。

## 29. 最小実行パス

Phase00 は最小実行パスを 1 本以上保証しなければならない。
canonical な最小実行パスを以下に固定する。

```text
Adapter normalize event
-> Phase01 intent export
-> Phase02 reaction export
-> Phase03 context export
-> Phase04 action export
-> Adapter handoff
```

この最小実行パスは以下を目的とする。

Core / Adapter / EventBus 境界の成立確認
trace_id の end-to-end 維持確認
action_type 決定主体が Phase04 であることの確認
world_command が Adapter 側に限定されることの確認

Phase05〜07 はこの最小実行パス成立後に追加する。
最小実行パス成立前に後続フェーズ固有ロジックを入れてはならない。

---

## 30. 例外仕様

fallback は許可する。
ただし以下を満たす場合に限る。

fallback は route を壊してはならない。
fallback は action_type の canonical 決定権を奪ってはならない。
fallback は world_command を生成してはならない。
fallback は trace_id を保持しなければならない。
fallback でも required export key を欠落させてはならない。

review path は例外経路ではあるが、契約経路であって bypass ではない。
review path を口実に phase を飛ばしてはならない。
